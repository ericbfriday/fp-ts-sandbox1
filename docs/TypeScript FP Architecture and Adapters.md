# **Functional Programming Architecture and Package Blueprint for Modern TypeScript Stacks**

Functional programming (FP) increases application health across Next.js, React, Hono, tRPC, TanStack libraries, and Better Auth by replacing implicit runtime hazards—untyped exceptions, leaky server/client boundaries, unvalidated transport payloads, and uncoordinated async side effects—with explicit, compiler-checked data flows. Because the November 2026 TypeScript FP landscape splits between unified effect runtimes (Effect 4.0 GA on September 30, 2026; Effect 4.1 on November 2, 2026\) and modular "functional-light" libraries (neverthrow, ts-pattern, Remeda v2, and Standard Schema), your personal package suite should avoid forcing a single runtime paradigm across every tier. Instead, the most resilient refactoring architecture uses **plain-object discriminated Result values and Standard Schema contracts as a universal cross-boundary language**, while isolating Effect v4 Context.Service and Layer graphs inside server and async-query interpreters.  
Three framework realities constrain how you should design and expose these packages. First, React Server Components (RSC), Next.js Server Actions, and tRPC serializers strip class prototypes across the wire, causing neverthrow instance methods to vanish upon transport and favoring plain-object Result representations or schema-backed codecs (patterns pioneered by @praha/byethrow and better-result v3). Second, Next.js and TanStack Start rely on **thrown sentinel values** for control flow (redirect(), notFound(), unauthorized(), forbidden()), so naive try/catch or fromThrowable wrappers silently break framework navigation unless they inspect and rethrow framework signals first. Third, Better Auth offers no official Effect package—a contributor in Better Auth issue \#7338 confirmed the team has no plans to build @better-auth/effect—and splits its surface across throwing server calls (APIError), tuple client objects ({ data, error }), single-slot middleware hooks, and sentinel-returning database hooks, requiring a normalizing adapter layer.

## **Strategic Architecture for Your Refactoring Packages**

Building internal packages to refactor existing codebases requires separating pure domain contracts from framework-specific runtime adapters. Your baseline TypeScript FP assessment documents that fp-ts v2.16 has merged into the Effect-TS organization, retains roughly 3.3 million weekly npm downloads according to package-tracking aggregators despite an "At risk" maintenance flag, and lacks general stack safety. New personal packages should therefore build zero new abstractions on fp-ts/HKT. Instead, split your monorepo into small, targeted packages spanning two interoperable tiers: a zero-runtime-dependency core for incremental refactoring at framework edges, and an optional Effect v4 runtime tier for complex backend orchestration, structured concurrency, and OpenTelemetry tracing.  
Choosing the right Result representation is the single highest-leverage decision for @fp/core. While neverthrow offers familiar .map(), .match(), and ResultAsync instance chaining within a single process, JSON and RSC serialization strips prototype methods from class instances—preserving data properties while breaking downstream .map() or instanceof calls unless explicitly rehydrated. Two newer 2026 libraries illustrate cleaner boundary primitives: @praha/byethrow models Result as plain serializable objects paired with tree-shakable namespace functions (R.pipe, Result.collect) and a unified sync/async API, while better-result (v3.0.1, released in 2026\) combines a serializable status: "ok" \| "err" discriminant with TaggedError classes, Result.gen short-circuiting, a dedicated Panic channel for unexpected defects, and schema-backed Result.codec boundaries. No independent runtime or bundle benchmark comparing neverthrow, @praha/byethrow, and better-result across RSC and RPC wires was found in current ecosystem documentation; these trade-offs come from package docs and maintainer comparisons. Adopting plain discriminated objects ({ status: "ok", value } \| { status: "err", error }) with pipeable Dual APIs (matching Remeda v2 and Effect conventions) in @fp/core keeps values serializable across RSC props, Server Actions, tRPC responses, and TanStack Query hydration without tree-shaking penalties.

Centering @fp/schema on the StandardSchemaV1 interface (\~standard.validate()) ensures your domain logic never locks into a single validation library. As specified by Standard Schema, \~standard.validate() may return either a synchronous result or a Promise, so @fp/schema should expose both parseSync (throwing a TypeError defect if an asynchronous schema is passed where synchronous execution is required, matching the spec's reference implementation) and parseAsync. By returning @fp/core Result objects carrying StandardSchemaV1.Issue arrays, the same schema can parse inputs at the boundaries of Next.js Server Actions, Hono routes, tRPC procedures, TanStack Router search parameters, and TanStack Form fields.  
import type { StandardSchemaV1 } from "@standard-schema/spec";

export type Ok\<T\> \= { readonly status: "ok"; readonly value: T };  
export type Err\<E\> \= { readonly status: "err"; readonly error: E };  
export type Result\<T, E\> \= Ok\<T\> \| Err\<E\>;

export type ValidationFailure \= {  
  readonly \_tag: "ValidationFailure";  
  readonly issues: ReadonlyArray\<StandardSchemaV1.Issue\>;  
};

export const ok \= \<T\>(value: T): Ok\<T\> \=\> ({ status: "ok", value });  
export const err \= \<E\>(error: E): Err\<E\> \=\> ({ status: "err", error });

export function parseSync\<S extends StandardSchemaV1\>(  
  schema: S,  
  input: unknown,  
): Result\<StandardSchemaV1.InferOutput\<S\>, ValidationFailure\> {  
  const out \= schema\["\~standard"\].validate(input);  
  if (out instanceof Promise) {  
    throw new TypeError("Schema validation must be synchronous at this boundary");  
  }  
  return out.issues  
    ? err({ \_tag: "ValidationFailure", issues: out.issues })  
    : ok(out.value);  
}

## **React and Next.js App Router: Guarding Process and Control-Flow Boundaries**

Modern React (including React 19.3.0, shipped September 9, 2026 per React release coverage) and Next.js (15 through 16.3) enforce strict server/client module graphs where conventional FP wrappers fail silently if process boundaries are ignored. Under React RFC 227, modules are implicitly shared across server and browser bundles unless explicitly marked with "server-only" or "client-only" poison pills or split via package.json conditional exports using the "react-server" condition. An industry blog guide on Next.js 16 reports 50–70% reductions in First Load JS when RSC boundaries are cleanly maintained, though no controlled independent benchmark in available documentation isolates FP wrapper packages as the cause. To make module separation compiler- and bundler-enforced in your personal packages, export pure types and Standard Schema parsers at the package root, gate Effect Layers and database/auth utilities under "react-server" (plus import "server-only"), and gate React hooks and error boundaries under "default" / "browser" (plus import "client-only"). Note that React 19.3.0 allows Server Components to render a Context exported directly from a 'use client' module, simplifying how parsed read-only session or configuration state flows down the tree without pulling client hooks onto the server.  
Inside Next.js Server Components, Route Handlers, and Server Actions, the sharpest FP trap is **thrown control-flow interruption**. Next.js implements notFound(), redirect(), permanentRedirect(), and dynamic request-time signals (such as cookies() under Partial Prerendering), along with experimental unauthorized() (401) and forbidden() (403) when experimental.authInterrupts is enabled, by throwing internal framework errors (NEXT\_REDIRECT, NEXT\_NOT\_FOUND, NEXT\_HTTP\_ERROR\_FALLBACK). Wrapping a server function in a generic Result.fromThrowable, Effect.tryPromise, or try/catch block catches these throws and converts navigation or auth interrupts into application Err values. Official Next.js documentation requires calling unstable\_rethrow(err) from next/navigation at the top of any catch block or promise .catch() handler before mapping errors. While a third-party tutorial erroneously claims unstable\_rethrow is Edge-only and imported from next/error, Next.js RFC \#64076 and official API docs confirm it works on both client and server from next/navigation. Critically, unstable\_rethrow does not inspect nested error.cause properties—wrapping a framework throw inside a custom domain error hides it from Next.js—and any resource cleanup (timers, locks, or fiber disposal) must execute prior to unstable\_rethrow or inside a finally block.  
For form mutations and user workflows, Next.js documentation explicitly mirrors FP design: **model expected errors as return values rather than thrown exceptions**, pairing Server Actions with React's useActionState. Throwing validation or domain failures inside a Server Action triggers the nearest client error.tsx boundary, destroys unsubmitted form state, and replaces server messages with an opaque production digest hash. Your @fp/next package should therefore expose a composable Server Action builder (createResultAction) that parses input through @fp/schema, runs typed auth context checks (or wraps next-safe-action with @next-safe-action/adapter-better-auth), protects execution with an unstable\_rethrow-first wrapper, and returns a plain-object Result directly consumable by useActionState. For truly unexpected defects, @fp/next can expose reusable wrappers built atop catchError from next/error (reported as stable in Next.js 16.3). Unlike generic react-error-boundary, catchError lets Next.js navigation throws propagate untouched, resets state on client navigation, and exposes retry() to re-fetch and re-render Server Components rather than merely clearing client state. Finally, remember that React Error Boundaries ignore exceptions inside imperative event handlers unless executed inside startTransition(() \=\> ...), and in light of the x-middleware-subrequest middleware bypass vulnerability, Next.js 16's proxy.ts (renamed from middleware.ts) should only run optimistic cookie redirects while true authorization stays inside your Data Access Layer and Server Action pipelines.  
import { unstable\_rethrow } from "next/navigation";  
import { err, ok, type Result } from "@fp/core";

export async function fromNextThrowable\<T, E\>(  
  fn: () \=\> Promise\<T\>,  
  mapError: (cause: unknown) \=\> E,  
  cleanup?: () \=\> void \| Promise\<void\>,  
): Promise\<Result\<T, E\>\> {  
  try {  
    return ok(await fn());  
  } catch (thrown) {  
    await cleanup?.();  
    unstable\_rethrow(thrown);  
    return err(mapError(thrown));  
  }  
}

## **Hono and tRPC: Resolving Type Accumulation and Dual Failure Channels**

Both Hono and tRPC rely heavily on TypeScript's structural inference to deliver zero-codegen RPC, which exposes both frameworks to compiler recursion ceilings and mismatched error transport models when FP primitives are added without care.

### **Hono Type-Graph Preservation and Problem Contracts**

Hono models middleware as a type-accumulating chain (MiddlewareHandler\<Env, Path, Input\>) where chained .use(), .get(), .post(), and validator calls refine Variables and validated request targets (json, form, query, param, header, cookie). Two type-level constraints govern any @fp/hono helper library. First, as explained in Fiberplane's Hono validation guide, detaching validation into a separate app.use() call rather than chaining it inline on the route handler severs target inference and causes c.req.valid(...) to collapse to never. Second, large Hono routers hit TypeScript's \~1,000-step instantiation depth cap (TS2589, unchanged in TypeScript 7.0). While Hono's official RPC docs recommend matching exact Hono versions across frontend and backend and pre-compiling declarations via emitDeclarationOnly (tsconfig.public.json) to speed up IDEs, contributors on Hono issue \#2399 note that ahead-of-time compilation only caches compute time and does not fix non-terminating TS2589 depth exhaustion on giant apps. Instead, @fp/hono should standardize **domain route-slice splitting**: keep the server router unified if desired, but export typed sub-router types so clients call hc\<UsersRoutes\> per slice rather than passing one monolithic AppType into hc.  
At runtime, Hono catches thrown errors inside handlers and middleware and routes them to app.onError() (so await next() never throws to upstream middleware), yet throwing introduces subtle HTTP bugs that @fp/hono should absorb. Because HTTPException.getResponse() has no reference to Context, throwing an HTTPException drops response headers already attached to c unless copied onto a fresh Response. Furthermore, documentation for hono-problem-details (tested against Hono \>=4.12.27, TypeScript 5.0–7.0, and Node.js \>=22) highlights that throwing inside app.onError() causes Hono to re-invoke onError repeatedly until the request rejects, and throwing behind compress() middleware can emit a Content-Encoding: gzip header on an uncompressed error body. On the validation layer, @hono/standard-validator (sValidator) works with any Standard Schema validator and exports flattenErrors, though callers must lowercase header keys (because Hono lowercases incoming headers), avoid putting validation regexes inside route paths (which fall through to 404 instead of running the param validator), and account for Hono's automatic HEAD-to-GET dispatch conversion. Consequently, @fp/hono should expose a resultToResponse helper that maps Ok and expected typed Err variants directly to explicit status-coded c.json(...) returns—preserving Hono RPC's status-code branching and avoiding HTTPException header loss—paired with an app.onError handler inspired by RFC 9457 Problem Details for unexpected defects.

### **tRPC v11 Dual Failure Channels and Reader Contexts**

tRPC v11 (shipping TanStack Query v5 integration, FormData support, React Server Components helpers, streaming responses, t.createCallerFactory, and native Standard Schema support on .input() and .output()) already incorporates clean Reader-like dependency injection. Using createContext to build per-request services and .use(({ ctx, next }) \=\> next({ ctx: ... })) middleware to narrow capabilities (such as verified user sessions) avoids fp-ts's contravariant environment-intersection conflicts while maintaining strict downstream type inference. While tRPC v11 accepts any Standard Schema library—allowing Valibot where edge/browser weight matters, as a PkgPulse comparative guide reports 1.37 KB for a login schema in Valibot versus 17.7 KB in standard Zod and 6.88 KB in Zod Mini—PkgPulse also notes that tRPC's TypeScript ergonomics and ZodError flattening utilities remain smoothest with Zod.  
The primary FP impedance mismatch in tRPC is the **two failure channels problem**, analyzed in depth by result-rpc. Globally, tRPC procedures throw TRPCError formatted by a single router-wide errorFormatter (note from tRPC community support that mutating opts.error inside onError does not alter what the client receives; onError is for logging/side effects, whereas errorFormatter shapes client errors). Because errorFormatter is global, TRPCError cannot express a closed, procedure-specific domain error union E on query.error. Conversely, returning a neverthrow or Result inside query.data cripples TanStack Query's runtime: retries, throwOnError, Error Boundaries, and offline pausing react only to query.error, not an Err nested inside query.data, and naive serialization strips TaggedError prototypes. To refactor existing tRPC routers cleanly, @fp/trpc should implement a dual-channel bridge modeled on result-rpc: on the server, wrap procedures with a resultProcedure helper that encodes expected domain Result errors cleanly while routing unexpected thrown bugs to an onInternalError logger and a sanitized INTERNAL\_SERVER\_ERROR via errorFormatter; on the client, pair @trpc/tanstack-react-query with a boundary reconstructor that validates the wire envelope, restores TaggedError matching, and lets outer UI shells subtract handled error tags (such as Unauthorized or offline transport failures) so leaf components exhaustively match only their domain errors.

## **TanStack Ecosystem: Search Contracts, Cooperative Cancellation, and Server Functions**

Across TanStack Router, Start, Query, Form, and Store, functional patterns eliminate whole classes of state drift, race conditions, and resource leaks. **TanStack Router** operationalizes "parse, don't validate" for URL search parameters: validateSearch accepts any Standard Schema library natively (including Zod v4, Valibot, ArkType, Effect Schema, or nuqs 2.5.0+'s experimental createStandardSchemaV1 with { partialOutput: true }), routing malformed URLs deterministically to VALIDATE\_SEARCH error components. Its explicit from constraint on useParams and useSearch enforces lexical provenance instead of global parameter guessing, while beforeLoad threads typed, inherited context through the route hierarchy. **TanStack Form** likewise consumes Standard Schema directly at field and form levels (typing state.errorMap.onChange cleanly by field key), runs synchronous validation before debounced asynchronous validation, and exports createFormHook, withForm, and withFieldGroup for composable form slices. When building helpers atop **TanStack Store** and Form, import useSelector directly from @tanstack/react-store rather than useStore, as useStore was deprecated in @tanstack/react-form v1.33.0+ and @tanstack/react-store.  
In **TanStack Start**, Vite compiles every createServerFn into three targets—a server RPC handler, a zero-HTTP SSR runner (createSsrRpc), and a client fetch stub (createClientRpc)—alongside explicit environment boundaries (createServerOnlyFn, createClientOnlyFn, createIsomorphicFn). Still, TanStack Start issues reveal sharp edges that @fp/tanstack should smooth over. First, an open issue (TanStack/router\#6428) shows that when .inputValidator() fails with Zod, Start JSON-stringifies the issues array into error.message, erasing structured validation errors on the client; @fp/tanstack should therefore supply a custom error SerializationAdapter (fromSerializab\[span\_209\](start\_span)\[span\_209\](end\_span)le) or an inputValidator wrapper that preserves field issues as structured Result values. Second, the same issue documents that createMiddleware({ type: 'function' }).server() enforces a literal type marker ('use functions must return the result of next()': true) that rejects custom { success: false, error } return objects in TypeScript even though Start serializes them at runtime. Isolating the single narrow as never escape hatch inside a shared @fp/tanstack middleware factory keeps application handlers strictly typed without repeating casts. Third, a resolved December 2025 issue (TanStack/router\#6010 on Start 1.132.0) demonstrated how global function middleware wrapping next() in try/catch can intercept redirect() responses before serialization unless redirects are checked first and callers use useServerFn where router redirect integration is expected. Note also that current Start APIs use .inputValidator() rather than .validator(), a naming shift that frequently trips older mocks and LLM code generation.  
For **TanStack Query (v5)**, the highest-value FP primitive is **cooperative cancellation paired with HTTP error guarding**, demonstrated by the community effect-query library (which illustrates these primitives using Solid Query accessor examples alongside core query-core semantics). Native fetch resolves rather than rejects on HTTP 4xx/5xx responses—causing TanStack Query to cache error pages as success data unless checked manually—while manual useEffect fetching invites stale-response races. Wrapping queryFn in @fp/tanstack so QueryFunctionContext.signal (AbortSignal) interrupts an Effect fiber or forwards into Result.tryPromise / fetch ensures that unmounting the last observer or calling queryClient.cancelQueries immediately cancels in-flight HTTP work and runs Effect resource finalizers. If you pair TanStack Query with an Effect layer, follow effect-query's lifecycle split: share one lazily constructed runtime in the browser (disposing on import.meta.hot?.dispose and discarding failed layer builds so Query retries can recover), but instantiate runtimes **per request on the server** so SSR requests never share state. Configure Query's retry predicate to exclude non-transient 4xx typed failures while surfacing unexpected defects to Error Boundaries.  
import { err, ok, type Result } from "@fp/core";

export type FetchFailure \=  
  \| { readonly \_tag: "HttpError"; readonly status: number; readonly body: string }  
  \| { readonly \_tag: "NetworkError"; readonly cause: unknown };

export async function fetchResultJson\<T\>(  
  input: RequestInfo \| URL,  
  init: RequestInit & { signal: AbortSignal },  
  parse: (raw: unknown) \=\> Result\<T, unknown\>,  
): Promise\<T\> {  
  let res: Response;  
  try {  
    res \= await fetch(input, init);  
  } catch (cause) {  
    throw { \_tag: "NetworkError", cause } satisfies FetchFailure;  
  }  
  if (\!res.ok) {  
    throw {  
      \_tag: "HttpError",  
      status: res.status,  
      body: await res.text(),  
    } satisfies FetchFailure;  
  }  
  const parsed \= parse(await res.json());  
  if (parsed.status \=== "err") throw parsed.error;  
  return parsed.value;  
}

## **Better Auth: Unifying Split Error Surfaces and Effect Interoperability**

Better Auth ships rich primitives—Web Standard Request/Response mounting, database adapters, plugins (organization, jwt, multiSession, deviceAuthorization), and framework cookies—yet forces application code through **four incompatible error and hook conventions**. On the server, auth.api.\* methods throw APIError exceptions identified via isAPIError(err). On the client, authClient.\* (backed by better-fetch and nanostores) returns { data, error } objects unless globally configured with fetchOptions: { throw: true }, forcing repetitive \`if (error \|  
\| \!data)narrowing and variable renaming across sequential calls\[span\_247\](start\_span)\[span\_247\](end\_span)\[span\_248\](start\_span)\[span\_248\](end\_span). In endpoint hooks,hooks.beforeandhooks.aftereach accept only a \*\*single\*\*createAuthMiddleware(ctx)callback rather than an array (as explicitly noted in Better Auth's official hook docs, overriding community bot examples), pushing teams into monolithicif (ctx.path \=== ...)routing blocks where failures throwAPIErrororctx.redirect(...)\[span\_249\](start\_span)\[span\_249\](end\_span)\[span\_250\](start\_span)\[span\_250\](end\_span). Meanwhile, databaseHooks use sentinel returns (falseto abort,{ data }to transform) or thrownAPIError\` instances.  
A robust @fp/better-auth package should also guard against four documented Better Auth operational pitfalls. First, invoking auth.api.getSession inside Next.js Edge middleware throws The edge runtime does not support Node.js 'perf\_hooks' module; edge proxy.ts / middleware should check cookies optimistically via getSessionCookie or getCookieCache, keeping auth.api.getSession in Node Server Components and Data Access Layers. Second, in Better Auth v1.4+ with cookieCache enabled, the default cache strategy shifted from base64-hmac to encrypted JWE/JWT, and Next.js 16 requires calling headers() or cookies() *outside* cached functions and passing them explicitly into getSession({ headers })—otherwise getSession silently returns null (and issue \#7008 also notes user reports of 300-second cache-expiration surprises when session cache settings misalign). Third, Server Actions that mutate session cookies require nextCookies() (Next.js) or tanstackStartCookies() (TanStack Start) registered as the **last** plugin in betterAuth({ plugins: \[...\] }). Fourth, databaseHooks omit auth.api deliberately to avoid circular calls—invoking auth.api.getSession inside session.create.before can trigger re-entrant session reads and updates, so database hooks should use ctx.context.internalAdapter, preserve all default fields such as image and id when returning { data } (preventing issue \#2098's Unknown argument image adapter crash), and keep before hooks idempotent because MongoDB transactions can re-run before hooks on write conflicts.  
To unify this surface, @fp/better-auth should provide three small, high-leverage helpers. First, expose runAuthApi and wrapAuthClient to normalize both throwing auth.api.\* calls and { data, error } client tuples into @fp/core Result\<T, AuthFailure\> values. Second, build composeAuthHooks to compile an array of pure { name, match, handle } predicates into Better Auth's single createAuthMiddleware slot, allowing auth rules to live modularly alongside feature modules. Third, for teams adopting Effect v4, mount Better Auth's Web handler via the officially documented HttpEffect.fromWebHandler(auth.handler) and expose a request-scoped CurrentUser / BetterAuthService using Effect v4's Context.Service class pattern to achieve the benefits outlined in Better Auth issue \#7338 without waiting on an official plugin.  
import { createAuthMiddleware, isAPIError } from "better-auth/api";  
import { err, ok, type Result } from "@fp/core";

export type AuthMiddlewareCtx \= Parameters\<Parameters\<typeof createAuthMiddleware\>\[0\]\>\[0\];  
export type AuthHookRule \= {  
  readonly name: string;  
  readonly match: (ctx: AuthMiddlewareCtx) \=\> boolean;  
  readonly handle: (ctx: AuthMiddlewareCtx) \=\> Promise\<unknown\>;  
};

export const composeAuthHooks \= (rules: ReadonlyArray\<AuthHookRule\>) \=\>  
  createAuthMiddleware(async (ctx) \=\> {  
    for (const rule of rules) {  
      if (rule.match(ctx)) {  
        const out \= await rule.handle(ctx);  
        if (out \!== undefined) return out;  
      }  
    }  
  });

export type AuthFailure \=  
  \| { readonly \_tag: "BetterAuthApiError"; readonly status: string \| number; readonly message: string }  
  \| { readonly \_tag: "UnexpectedAuthError"; readonly cause: unknown };

export async function runAuthApi\<T\>(op: () \=\> Promise\<T\>): Promise\<Result\<T, AuthFailure\>\> {  
  try {  
    return ok(await op());  
  } catch (e) {  
    if (isAPIError(e)) {  
      return err({ \_tag: "BetterAuthApiError", status: e.status, message: e.message });  
    }  
    return err({ \_tag: "UnexpectedAuthError", cause: e });  
  }  
}

## **Static Enforcement, Linting, and Incremental Refactoring Playbook**

FP primitives preserve long-term health—especially when AI coding agents refactor your codebase—only when anti-patterns fail static analysis automatically. As of November 2026, static enforcement divides cleanly along your runtime boundary. On the **Effect v4 track**, @effect/tsgo (wrapping TypeScript-Go / tsrs) and the Effect Language Service added 16 new diagnostic rules and tsrs \--lint support (effect-tsgo \--tsrs-lint oxlint \--type-aware or effect-tsgo \--tsrs-lint=latest vp lint). Those diagnostics directly police structural FP discipline: effectInFailure, effectInVoidSuccess, effectTryWithoutCatch, runEffectInsideEffect, schemaSyncInEffect, strictEffectProvide, tryCatchInEffectGen, abortControllerInEffect, asyncFunction, and globalJsonInEffect.  
On the **Functional-Light (Result) track**, the essential static guard is a type-aware rule ensuring callers never ignore a returned Result. Rust-based **Oxlint** paired with oxlint-tsgolint (oxlint \--type-aware) delivers dramatic speedups—developer articles report 20–40x gains with tsgolint and 50–100x overall, dropping toward 6x when JS plugins run—and Oxlint documentation reports coverage for 59 of 61 typescript-eslint type-aware rules.
